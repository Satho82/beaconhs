## 2. Canonical maintenance contract (D01)

### Aggregate and lifecycle

The canonical aggregate is:

```text
Maintenance Issue
  → triage
  → assignment
  → Work Order when required
  → resolution
  → verification
  → closure
```

The canonical persistence foundations are `maintenance_issues` and `maintenance_work_orders`. `maintenance_issues` is the authoritative problem/report record; a work order is an optional execution record for that issue. A Work Order must not become an independent competing report/physical-work lifecycle.

The canonical engine accepts approved source adapters for Front Office, Staff, Guest QR, Staff QR, Inspection/Audit, Scheduled tasks and approved integrations. An adapter supplies source metadata and validates its own source context; it must then call/use the same issue creation, entitlement, property access, attachment validation, audit and lifecycle rules as native maintenance.

### Assets and equipment

Canonical maintenance must support an optional equipment/asset association. The chosen association must resolve to exactly one authorized hotel property for property-owned records. A room association likewise resolves through floor/building to property. Future source adapters must not insert a second work-order table or bypass the canonical Issue.

### Safe convergence from `equipment_work_orders`

`equipment_work_orders` remains a documented pre-V1.4 asset/PPM record until a forward-only convergence work package is approved. The safe strategy is:

1. Do not delete, rewrite, or lose historic equipment work-order rows.
2. Introduce the canonical maintenance issue/work-order shape and an explicit legacy/mapping relationship only after schema/RLS/audit design is approved.
3. Route **new V1.4 physical maintenance work** through the canonical engine; preserve legacy records read-only or with a clearly bounded legacy lifecycle during migration.
4. Provide an idempotent, auditable backfill/mapping plan only if records can be mapped without inventing facts. Unmappable history stays historical.
5. Retire independent new-record creation from the equipment-work-order UI only after parity and migration verification. Transitional links/redirects may exist; two operational engines may not.

This contract intentionally preserves historic data while preventing new divergence.

## 3. Action Plan contract (D02)

`corrective_actions` is the canonical V1.4 Action Plan item. It retains its lifecycle, owner, due date, verification, evidence, flows, audit and reports. No Action Plan table or duplicate engine is authorized.

### Approved source model

The only Action Plan source kinds are:

- Compliance
- Risk
- Inspection / Audit
- Incident
- Staff Training
- Manual

Maintenance is explicitly not a source kind. If an action requires physical work, the Action Plan item may request/create a **linked canonical Maintenance Issue**. That issue retains its own maintenance source and lifecycle.

Subsequent design must replace reliance on `sourceEntityType`/`sourceEntityId` free text as the sole reporting or integrity mechanism. It must define a typed source relation/registry with validated source kind, tenant identity, source record identity, and source-property resolution where applicable. Domain-specific foreign keys may be introduced when they provide an enforceable relationship; a governed source-link table is acceptable where a heterogeneous set requires it. The design must prevent cross-tenant links and reject unapproved source kinds.

### Property and history

An Action Plan item is property-owned only when its source or operational intent is specific to a property. It is tenant-wide otherwise. A property-owned item has mandatory property identity and property RLS; it must not use a nullable `property_id` merely for selector appearance. Links to Maintenance are distinct from source links and are historically preserved.

## 4. Configuration inheritance, versions and history (D03)

V1.4 defines a generic governance foundation, not one generic replacement schema for all domain data:

```text
Uvanoo Platform Standard
  → immutable Platform Master Version
  → tenant adoption
  → tenant-owned configurable copy/version
  → property applicability
  → operational use
  → immutable operational reference/snapshot
```

### Required semantics

| Concept                       | Contract                                                                                                                                                     |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Platform master               | Platform-owned standard. Tenant edits can never mutate it.                                                                                                   |
| Platform version              | Immutable once published; has author/time/audit metadata.                                                                                                    |
| Tenant adoption               | Records the platform source/version and creates or associates a new tenant-owned copy.                                                                       |
| Tenant version                | Drafts may change; published versions are immutable; archive/inactive prevents new operational use but preserves history.                                    |
| Source lineage                | Tenant copy/version records the originating platform master/version where adopted; independently created tenant material has an explicit no-platform origin. |
| Property applicability        | A join/policy model, not duplicated per-property editable masters. It chooses where a published tenant configuration can operate.                            |
| Operational historical record | Captures an immutable version reference and a snapshot when the domain requires self-contained historic rendering/assessment.                                |
| Audit                         | Create/adopt/edit/publish/archive/applicability changes are tenant/platform audited with actor and timestamp.                                                |

`form_templates` and `form_template_versions` are reusable where the configuration is a form; their immutable response version reference remains canonical. `risk_templates` and assessment/signoff snapshots are reusable specialized domain patterns. Inspection, compliance, training and other domains may remain specialized, but must use the governance contract rather than duplicate incompatible adoption/state concepts.

## 5. Property ownership and people/property assignment (D04)

### Ownership matrix

| Domain record                                           | Classification                                                                      | Required relationship and scope rule                                                                                                  |
| ------------------------------------------------------- | ----------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| Maintenance Issue / Work Order                          | Property-owned                                                                      | Exactly one hospitality property, directly or through a validated room/asset/location relation; property RLS and direct-action check. |
| Risk Assessment                                         | Property-owned                                                                      | Existing `risk_assessments.property_id`; preserve property predicate and signoff snapshot.                                            |
| Hotel Handover                                          | Property-owned                                                                      | Existing property-aware handover contract.                                                                                            |
| Meter / tariff / meter reading                          | Property-owned                                                                      | Meter resolves to property; reading preserves currency/cost snapshot.                                                                 |
| Daily Hotel Data                                        | Property-owned                                                                      | Tenant + property + operational date unique identity.                                                                                 |
| Operational compliance status/dispatch                  | Property-owned only when standard/applicability and execution are property-specific | Otherwise tenant-wide/person/role scoped. Do not fabricate property ownership.                                                        |
| Inspection/Audit execution                              | Property-owned when performed at a property                                         | Template itself is property-applicable.                                                                                               |
| Incident                                                | Property-owned when occurrence is at a property                                     | Otherwise tenant-wide; explicit occurrence/location semantics required.                                                               |
| Asset                                                   | Property-owned when located/operated at a property                                  | Asset may have controlled relocation history; no ambiguous simultaneous property ownership.                                           |
| Action Plan                                             | Property-owned only for property-specific action                                    | Otherwise tenant-wide; source/intent controls classification.                                                                         |
| Templates, standards, requirements, risk standards      | Property-applicable                                                                 | Tenant-owned published versions applied through applicability; not property-owned copies by default.                                  |
| People, courses, departments, job titles, tenant config | Tenant-wide with optional property relations                                        | No property requirement solely for filtering.                                                                                         |
| Reports/dashboards                                      | Tenant-wide with explicit applicable/property dimensions                            | Run results must apply authorized query scope.                                                                                        |

### People model

The identity chain is: global authentication `users` → tenant membership `tenant_users` → optional tenant person/staff `people`. `roles`/`role_assignments` grant RBAC permissions and scopes. `people_titles`, departments and job roles are employment/operational metadata. They are not permission grants and may not be used to infer property access.

A person may have zero, one or many property assignments. The future assignment model must carry tenant, person/membership identity, property identity, assignment state and suitable operational metadata. A Cluster GM can receive multiple property assignments and a role scope covering those properties. A Management Company Admin may have tenant-wide role scope. A single-property user has only the specific property scope. Authoritative access remains RBAC/RLS, not the staff directory or title.

## 7. Tenant general settings and money contract (D06)

Tenant General owns: enabled/default locale, IANA timezone, date format, number format and default ISO 4217 currency code. Currency and locale are separate values. Valid examples include `GBP`, `EUR`, `USD`, and `AED`; formatting locale never determines currency.

Financial UI must obtain a tenant-default currency through a shared configuration resolver, not a literal symbol/code. Existing metering tariff/readings already demonstrate the necessary per-transaction currency snapshot. Costs, revenue and financial reports must preserve the applicable currency code/snapshot with historical values whenever later default changes would otherwise alter meaning. Known baseline literals/defaults (`GBP` in metering entry and `USD` in corrective-action financial rendering) are Work 03+ remediation targets, not authorization to edit in Work 02.

## 8. Daily Hotel Data contract (D07)

Daily Hotel Data is a new canonical, structured, property-owned operational dataset. It must not be represented as a generic task/checklist or fictional KPI feed.

**Identity:** one current controlled record per `(tenant_id, property_id, operational_date)`. `operational_date` is interpreted in the property/tenant operating timezone defined by the eventual timezone contract.

**Captured fields:** date; rooms available; rooms sold; rooms occupied; room revenue; out-of-order rooms; arrivals; departures; in-house guests; VIPs; PEEP; optional notes. Room availability defaults from configured property inventory, but the captured daily number can be reconciled through an explicit adjustment/reason/history rule.

**Read-only calculations:**

- `occupancy_percent = rooms_sold / rooms_available`, when rooms available is positive;
- `ADR = room_revenue / rooms_sold`, when rooms sold is positive;
- `RevPAR = room_revenue / rooms_available`, when rooms available is positive.

Undefined denominators render as unavailable, never zeroed fictional values. Room revenue uses the tenant currency and snapshots its code. Corrections require an auditable revision model: original submitted values/history are retained, with correction actor/time/reason; current view resolves the current revision. Future PMS integration must explicitly define authoritative synchronization/supersession; until then commercial dashboard data is derived from this dataset only.

## 9. Communications contract (D08)

V1.4 Communications is limited to system-generated operational notifications, reminders, escalation notifications, approved configurable recipient rules, approved email/SMS/push delivery, and delivery/history status where appropriate. It reuses notification preferences, event fan-out, jobs, provider resolution, email/SMS/push channels and audit patterns.

Tenant configuration can select permitted operational rules only within Platform capability. It must not become marketing CRM, contact prospecting, campaign segmentation, newsletter publishing or campaign analytics. Any recipient rule must be entitlement/permission aware, tenant-bound, property-aware where relevant, auditable and unable to expose cross-tenant data.

## 10. Governed import/export contract (D09)

There is one framework and one lifecycle:

```text
Download template → upload → parse → preview → validate → map → detect duplicates
→ show errors/warnings → explicit confirmation → transactional import → audit result
```

Initial dataset handlers are Property Structure (properties/buildings/floors/rooms/room types), People, Compliance Registry and Assets. They share framework lifecycle, permissions, audit, retention and status semantics; they own only typed row validation/matching rules.

### Import rules

- A create never silently overwrites an existing record.
- An update is allowed only when its dataset declares explicit matching keys, the preview labels it as an update, and the authorized operator explicitly confirms it.
- A confirmed import is transactional at the approved batch boundary. Validation/authorization failures must not produce silent partial success.
- Result data identifies accepted, rejected, warning, duplicate, created, updated and skipped rows and provides safe error detail.
- Upload files use private storage, tenant-bound access, a defined retention/expiry policy and an audit trail. Sensitive source content is not exposed in generic logs.
- Exports apply the same tenant/property/RBAC scope as UI/API queries, are auditable, and never use navigation hiding as authorization.

## 11. Tenant cloning contract

Tenant cloning creates a **new tenant-owned configuration workspace** from a selected source tenant or approved baseline. It is not tenant duplication, credential cloning, operational-data replay or cross-tenant identity sharing.

Every copied row receives new tenant-owned identifiers and references are remapped within the clone transaction/workflow. The source tenant is read-only throughout. Clone execution is Platform Admin-only, explicitly target-tenant scoped, audited, idempotently identifiable and failure-safe (no partially usable target tenant).

### Selectable clone scopes

| Selectable scope           | May copy                                                                                                                                                            |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Tenant general/branding    | Non-secret tenant configuration and approved branding references only under a separate asset-copy policy.                                                           |
| Organization configuration | Departments, job titles, non-identity groups and approved structure.                                                                                                |
| Module/configuration       | Entitlement-compatible module settings, adopted templates, standards, maintenance/risk/compliance/audit configuration, dashboard configuration, notification rules. |
| Property structure         | Properties, buildings, floors, rooms and room types, only when selected.                                                                                            |
| Integration configuration  | References/configuration only if secrets are independently re-entered or an approved secure secret-clone policy exists.                                             |

Never clone authentication credentials, existing memberships as credentials, audit history, operational incidents, completed maintenance/inspection history, historical evidence, sensitive uploaded documents, delivery history, or any other operational history. A clone may create new invitations/assignments only through a separate explicit process; it must not clone a user's authentication authority.

## 12. Demo/test reset safety contract

No reset is implemented or authorized by this work. Future reset is a tightly controlled **tenant-scoped operational-data reset job**, never a generic database wipe.

It must be available only in designated demo/test environments through Platform Admin authority; be compile/runtime environment guarded; reject production identifiers/hosts; require target-tenant selection, typed confirmation, a reviewed scope preview and explicit preservation choices; record audit events before/after; and use a bounded allow-list of removable operational domains.

It may preserve selected tenant structure/configuration while clearing explicitly selected demo operational records. It must never delete data outside the confirmed target tenant, must not run from ordinary tenant administration, and must use non-destructive/recoverable or backup-verified mechanisms appropriate to the future environment policy. “Wipe database”, unscoped SQL and production execution are prohibited.

## 14. Active property / portfolio scope contract

The selector expresses an authorized working context only:

```text
All My Properties / Portfolio = every and only property authorized by current RBAC scope
Specific property = one property already authorized by current RBAC scope
```

For a Cluster GM assigned Hotels A and B, the selector has exactly Portfolio, Hotel A and Hotel B. A single-property user cannot select or obtain Hotel B. A management-company admin can have authorized tenant portfolio scope. A Platform Super Admin switches tenants only via Platform permissions; platform privilege does not imply uncontrolled tenant application data queries.

### Required query contract

1. Resolve active tenant and authenticated `RequestContext` first.
2. Resolve effective RBAC property scope (`tenant`, approved property set, or no properties) server-side.
3. Resolve the selector preference only against that authorized set. The cookie/URL/client value is untrusted input.
4. For portfolio, query the server-authorized set; for selected property, intersect/narrow to the selected authorized ID.
5. Apply tenant RLS plus action-property configuration and module-specific property predicates in the database transaction.
6. For direct-ID reads/mutations/API routes, load/verify the parent property and assert property access; client filters and navigation visibility are never sufficient.
7. A module may expose the selector only when it can apply the contract. Tenant-wide records remain tenant-wide, and property-applicable records filter by applicability, not invented ownership.

## 15. Module entitlement/access contract

Every access path follows this order:

```text
Platform module catalogue
  → tenant entitlement (including effective dates)
  → property availability/applicability when relevant
  → role permission and scoped assignment
  → user access to route/action/API/query
  → navigation visibility as final UX expression
```

The existing `tenant_module_entitlements`, `assertTenantModuleEntitled`, permissions/role assignments, RequestContext and RLS are the starting point. Navigation is a UX result only; hidden navigation cannot secure a page, server action, route handler, download, attachment, background job or API. Each such entry point repeats/enforces the applicable contract.

## 16. No-fake-functionality Definition of Done

A meaningful interactive element is complete only if the entire vertical path is complete:

```text
UI → permission → canonical data → server action/API → validation
→ tenant/property isolation → audit/history → success/error UX → automated test
```

This means no decorative buttons, mock saves, fake dropdown configuration, placeholder charts, hard-coded production KPIs, client-only security filters, or exports/imports that do not operate. A filter must constrain server-authorized data. A configuration value must persist, be read by the intended canonical engine and have tested effects. Empty, loading, error, authorization and deleted/archived states must be truthful. A polished screen without the chain above is incomplete.

## 17. Data/history immutability and RLS rules

1. Tenant customization never updates a Platform master.
2. Published configuration and template versions are immutable; revise through a new version.
3. Completed/issued/assessed operational records preserve version identity and, when necessary for durable historic interpretation, immutable snapshots.
4. Financial records preserve currency code/value snapshots when required to retain meaning after tenant defaults change.
5. Correcting Daily Hotel Data or operational facts preserves prior revision, actor, time and reason; it never silently replaces history.
6. Historic equipment work orders, evidence and audit history are never destructively removed as part of maintenance convergence.
7. Every new tenant table has `tenant_id`, tenant-bound foreign keys/indices, RLS registration and tenant-bound transaction execution. Every property-owned table has a tested property predicate/policy plus direct parent/action authorization.
8. Super-admin transactions are deliberate exception paths; background jobs establish tenant context before reading/mutating tenant data.
9. Attachments remain private and accessible only through an authorized tenant/property-scoped parent relationship.
