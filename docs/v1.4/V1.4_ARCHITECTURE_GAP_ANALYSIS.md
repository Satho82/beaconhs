# Uvanoo V1.4 architecture and gap analysis

**Status:** analysis only; no V1.4 implementation, deployment, migration, container build, or production/staging access was performed.

## 1. Executive summary

The inspected V1.3.1 Hotfix.2 lineage already has credible multi-tenant foundations: tenant-bound transactions and RLS, scoped role assignments, module entitlements, audit logging, a form/version engine, a compliance engine, document versions, notifications, jobs, reports, and a hospitality property hierarchy.

The V1.4 implementation should be an extension/consolidation programme, not a greenfield rewrite. The strongest reusable V1.4 foundations are `form_templates`/`form_template_versions`, `compliance_*`, `corrective_actions`, `risk_*`, `hospitality_*`, `tenant_module_entitlements`, `roles`/`role_assignments`, and the audit/event/job packages.

The most material architectural issue is maintenance. Hospitality reports, including guest QR reports, correctly enter `maintenance_issues` and optional `maintenance_work_orders`; however `equipment_work_orders` also exists as a separate physical-work model. The schema comment expressly says hospitality records do not reuse it. V1.4 must approve a single canonical issue/work-order aggregate and an asset link before extending more entry points. A second engine must not be introduced.

Other priority gaps are: a single configuration inheritance model, a product-wide active-property filter, an explicit Action Plan source contract, centralized business configuration and currency, repeatable transactional bulk import, and a canonical division between Tenant Settings and Platform Admin.

## 4. Canonical engine map

### Maintenance — decision required before Work 02

**Existing hospitality intake path:** room/property hierarchy or public QR → `createRoomMaintenanceIssue` / `submitGuestMaintenance` → `maintenance_issues` → optional one-to-one `maintenance_work_orders` → issue evidence/audit. `maintenance_issue_source` already enumerates `staff`, `front_office`, `manager`, `engineering`, `staff_qr`, `guest_qr`, `inspection`, `scheduled_task`, and `api_integration`. Entitlement `hospitality.maintenance`, `maintenance.*` permissions and explicit property checks protect the authenticated path; public QR validates token, tenant/module state, input, consent, rate limits and uploads.

**Conflicting engine:** `equipment_work_orders` is separately used by the asset/PPM area. `hospitality.ts` explicitly documents that hospitality records do not reuse construction `equipment_work_orders`. This is a real duplicate physical-work model, not merely a route alias.

**Recommendation:** retain `maintenance_issues` as the V1.4 report/triage/work-order aggregate because it already covers front-office, staff and guest QR. In a foundational package, either replace/converge `equipment_work_orders` behind that aggregate or make it a compatibility projection with no independent lifecycle. Add an optional `asset_id`/equipment relationship, source-reference contract and explicit property identity to the canonical record. Do not create an Action Plan-maintenance source; an Action may instead create a linked maintenance issue.

### Action Plan

`corrective_actions` is the nearest reusable canonical engine: status/lifecycle, owner, due date, verification, evidence, audit, flows and reports already exist. It is not yet an approved V1.4 Action Plan:

- source enum is limited to inspection/incident/near miss/observation/audit/JSA/other;
- source identity is polymorphic, except a form-response shortcut;
- no property ID or property RLS predicate exists;
- `costImpact` reporting formats hard-coded USD in two pages;
- no first-class links for compliance, risk, staff training or manual source classification.

Extend it, do not create a second action table. The approved source allow-list must be: Compliance, Risk, Inspections/Audits, Incidents, Staff Training, Manual. Maintenance must only be a linked consequence.

### Templates

`form_templates` + `form_template_versions` is the best Common Template Builder base: published versions are immutable; responses retain `templateVersionId`; the builder has schema validation, scoring, conditional logic, workflow, automation, PDF and evidence support. The inspection, risk, equipment and training schemas have specialized parallel template/configuration tables. V1.4 should introduce a governance/adoption layer around the form engine and selectively map specialized modules, rather than replace all specialized tables at once.

### People identity model

Authentication is a global Better Auth `users` identity. `tenant_users` is the active tenant membership. `people` is the tenant person/staff record and can link to a user; `people_assignments` and organisation records represent work assignment. `roles` + `role_assignments` express application permission and scoped access. Job titles are `people_titles` and job-title tasks, and must remain business/HR metadata, not RBAC. V1.4 property assignment should be explicitly represented/derived in the people/member assignment model and synchronize only through role scope rules, never through job title.

## 6. Configuration and inheritance assessment

The repository has three useful but non-uniform patterns:

1. **Forms:** tenant-owned template + immutable versions and response version references.
2. **Risk:** platform or tenant templates; assessments record adopted version and a JSON snapshot; sign-offs snapshot the assessment.
3. **Platform/tenant settings:** mostly separate records and provider fallback, rather than a generic adopted-copy lineage.

There is no universal representation of: platform master ID/version → tenant adopted copy → property applicability → draft/published/archive state → immutable operational snapshot. Risk's `ownerKey` and snapshot is closest, but an editable tenant copy lineage is not expressed.

**Smallest recommended extension:** introduce a generic, tenant-scoped `configuration_adoptions`/`configuration_versions` foundation (or extend the form template domain where only forms are needed) with `platform_master_id`, `tenant_copy_id`, source version, lifecycle state, tenant ownership, copied-at/adopted-by metadata, and property applicability join rows. Require every generated/completed record to store the immutable version/snapshot ID it operated under. Do not mutate a platform master due to tenant customization. This must be designed once and then consumed by template, compliance, risk and configurable reference datasets.

## 7. Active-scope assessment

The hospitality property switcher stores an untrusted cookie (`active_hospitality_property`). `resolveHospitalityPropertyContext` first queries authorized properties using server-side scope; `applyActiveHospitalityPropertyScope` narrows a transaction only after `assertCanAccessProperty`. This is a sound UX-only selector design for hospitality routes. RLS derives authority from role scope and transaction configuration, not the cookie.

## 9. Hard-coded configuration audit

System invariants that should remain code/DB constrained include authentication/authorization mechanics, permission identifiers, RLS scope modes, storage security limits, immutable lifecycle rules, allowed upload MIME classes, and state-machine transition safety.

Business configuration currently embedded in enum, constants or UI and needing an ownership decision includes maintenance priorities (`low/medium/high/critical`) and source/status sets; risk template categories and fixed 1–5 scoring; risk validity values (3/6/12/24); room type free text; form/inspection/equipment/training type structures; incident classifications/injury types; notification policies; operational recurrence; and module-specific status/type labels. Some can remain system lifecycle invariants; tenant-adjustable business taxonomies should use adopted configuration records rather than duplicated UI constants.

Currency findings:

- metering stores ISO currency and reading snapshots correctly, but its tariff entry page defaults `currency` to `GBP` and formats with `en-GB`;
- corrective-action print and by-source reports hard-code `USD` for cost impact;
- no confirmed tenant-wide ISO currency setting was found.

V1.4 must define tenant `currency_code` (ISO 4217) and locale separately, use it as a UI default only, preserve transaction snapshots, and never infer currency from formatting locale.

## 10. Import/export assessment

Exports are relatively mature: report definitions/runs/schedules, PDF/CSV-oriented outputs, audit support, storage and worker queues exist. CSV helpers and a vehicle-log import policy demonstrate parsing/validation patterns. This is not a common bulk-import product.

Missing shared capabilities for properties/buildings/floors/rooms/types, people, compliance, assets and other approved configuration datasets are: template download with version ID, column mapping, in-browser/server preview, row warnings/errors, cross-file and existing-record duplicate rules, explicit confirmation, per-batch transactional persistence, rollback/compensation policy, result/audit record, downloadable error report, and a consistent authorization/property applicability check.

Recommendation: foundation package and `import_batches` / `import_batch_rows` (or equivalent) with typed dataset handlers. Parse and validate outside mutation; commit in a transaction per confirmed batch; reserve destructive updates behind explicit matching policy; produce audit/domain events. Reuse `@beaconhs/audit`, attachments/storage and jobs for durable processing; do not make each module invent an importer.

## 11. Security, RLS and test assessment

Evidence of good existing coverage includes tenant/property access, property delegation and action-scope tests; hospitality maintenance/QR/property-context contracts; RLS integration fixtures for hospitality metering; module-entitlement/nav policy tests; role assignment tests; risk, incident, inspection, training, compliance, form, document and attachment lifecycle contracts; audit tests; and worker scheduling/delivery tests.

Security-critical regression suite required before V1.4 implementation:

1. Tenant isolation and RLS for every new/adapted table, including tenant copy and property applicability joins.
2. Direct URL/action/API authorization for every property-scoped parent and attachment; untrusted active-property cookie must not expand access.
3. Multi-property portfolio vs single-property filtering across dashboard, report, maintenance, risk, Action Plan, inspection, incident, training, people, assets, metering and handover.
4. The one-maintenance-engine source path: front office, staff, guest QR, inspection and future source create the same canonical record without bypassing audit/entitlement/property checks.
5. Action Plan source allow-list; reject maintenance as source; verify only a linked maintenance issue can be created.
6. Platform master immutability, tenant-copy independence, property applicability, published/archive transitions and completed-record snapshots.
7. Import authorization, duplicate behavior, validation/no partial writes, idempotency, audit result and export scope.
8. Currency defaults/snapshots and reporting formatting.

No RLS weakening is justified. Several current modules lack a property ID, so their V1.4 property selector must remain absent or visibly tenant-wide until their data ownership/policy model is extended.

## 12. Proposed database evolution (no migrations written)

Remain unchanged initially: authentication users/sessions; tenants and memberships; role assignment architecture; form response/version model; document versions; attachments; audit/event/job/outbox; hospitality property hierarchy; existing risk snapshot model; module entitlement table.

Likely extensions:

- `tenants`: ISO currency and possibly operational default timezone/locale policy, with clear platform provisioning authority.
- `corrective_actions`: approved source kind, typed source links or source registry, optional `property_id`, linked canonical maintenance issue ID, and supporting tenant/property/source indexes.
- `maintenance_issues`: explicit property ID (or a normalized location/asset association that always resolves to one property), optional asset link and source-origin metadata; convergence path for equipment work orders.
- Existing compliance, inspection, incident, training and asset records: property ownership/applicability only where an operational record genuinely belongs to a hotel; avoid shallow nullable property IDs that cannot be enforced.
- Generic configuration adoption/version/applicability data: platform master, tenant copy/version lineage, lifecycle, property applicability join, immutable snapshot/reference linkage. Specialized form/risk models can be mapped incrementally.
- Import batch/run/row/error/audit data; store raw source securely only when retention policy permits.
