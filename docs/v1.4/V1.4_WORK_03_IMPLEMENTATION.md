# Uvanoo V1.4 Work 03 — Configuration + Tenant Defaults Foundation

## Scope delivered

Work 03 implements only the foundation approved in [Architecture Decisions](V1.4_ARCHITECTURE_DECISIONS.md). It does not implement Maintenance convergence, Action Plan changes, Daily Hotel Data, tenant cloning, demo reset/seed data, bulk import handlers or Work 04.

## Schema and migration

Migration `0054_v14_configuration_tenant_defaults.sql` is forward-only and non-destructive. It:

- adds `operational_locale`, `operational_timezone`, `date_format`, `number_format` and `default_currency_code` to `tenants`, with explicit safe defaults for existing rows (`en`, `UTC`, `medium`, `standard`, `USD`);
- adds format/currency database constraints without changing historic financial snapshots;
- adds `configuration_masters` and immutable `configuration_master_versions` for Platform standards;
- adds `tenant_configurations` and immutable published `tenant_configuration_versions` for tenant-owned copies and version lineage;
- adds `tenant_configuration_property_applicability` for selected-property applicability (no rows means tenant-wide applicability);
- adds `tenant_configuration_form_templates` as the forms-first binding boundary; and
- installs database triggers rejecting update/delete of published master or tenant configuration versions.

The existing Forms engine is not rewritten. Existing `form_templates`, `form_template_versions`, `form_responses` and their version provenance are unchanged. A governance configuration can bind to an existing same-tenant form template through a composite tenant foreign key; no form/schema/response is copied or migrated.

## Resolver and Tenant General Settings

`apps/web/src/lib/tenant-operational-defaults.ts` is the canonical server-side resolver and validator. It returns a typed `TenantOperationalDefaults` value and validates BCP 47 locale through `Intl.getCanonicalLocales`, IANA timezone through `Intl.DateTimeFormat`, ISO 4217 currency through `Intl.NumberFormat`, and the constrained date/number presentation choices.

`/admin/settings` now persists these defaults through the existing `admin.settings.manage` authorization guard and tenant-isolated update path. The audit event includes before/after default values. Invalid inputs fail before persistence.

## Governance, property security and audit

`apps/web/src/lib/configuration-governance.ts` provides the first reusable tenant operations:

- adopt a published Platform master version by value into a tenant-owned draft/version, retaining master/version lineage;
- set tenant configuration selected-property applicability after `admin.settings.manage` and server-side property authorization; and
- bind an existing tenant form template without mutating form data.

Each operation is recorded using the existing tenant audit engine in the same database transaction. The new tenant-owned tables are registered in `TENANT_SCOPED_TABLES`; the applicability table additionally receives the existing direct-property RLS predicate. Composite tenant foreign keys prevent cross-tenant configuration, property and form binding relationships.

Platform master creation/publishing remains intentionally unexposed in a tenant route: the schema and immutable version boundary are present, while Platform Admin surface/command work belongs to the future Platform Admin package. Tenant adoption can only select an already-published master/version.

## Currency remediation

- New metering tariffs now default to the tenant resolver's ISO currency rather than literal `GBP`; existing tariff/readings still render their own stored currency snapshot.
- Corrective-action cost rendering now uses the tenant default currency rather than literal `USD`, because the existing `cost_impact` model has no historical currency snapshot. A future Action Plan/cost evolution must add a record-level currency snapshot before financial history can be fully immutable across currency-default changes.

No historic meter tariff, reading, or other financial data was rewritten.

## Forward recovery and limitations

The migration is additive. Recovery is by forward corrective migration; it must not delete governance records, form history or financial snapshots. Database constraints validate structural values; full IANA/ISO validation is performed by the application resolver because PostgreSQL does not natively maintain the required canonical lists.

The following are deliberately deferred: Platform Admin commands/UI for authoring/publishing masters; operational use of governance configurations by specialist modules; property-assignment model; and a transaction currency snapshot for Action Plan costs.
